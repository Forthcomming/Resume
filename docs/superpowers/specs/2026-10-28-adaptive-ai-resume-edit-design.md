# 自适应 AI 简历优化链路设计

## 目标

解决普通 AI 优化只做同义替换、结果空泛的问题。在不引入多轮聊天、不修改 JD 定制流程的前提下，让系统根据当前内容的信息完整度决定直接改写或先追问关键事实。

## 范围

本轮只调整普通板块 / bullet AI 优化：

- AI 判断当前内容是否足以完成有价值的改写。
- 信息足够时直接生成建议。
- 缺少会影响真实性的关键事实时，先追问最多 3 个问题。
- 用户补充后生成建议；也可跳过追问并进行保守优化。
- Diff 中说明本次具体改进点。

不修改：

- 独立的 JD 定制版流程。
- 板块版本、保存、预览和 PDF 导出。
- DeepSeek 公共请求层及现有 API Key 机制。
- 普通优化不读取 JD、目标职位或其他简历板块。

## 现状问题

当前链路是“当前内容 + 一句指令 → 直接重写”。模型没有机会判断信息缺口，快捷指令也偏泛，因此容易出现：

- 只替换近义词或调整句式。
- 使用“负责、参与、提升”等空泛表达。
- 为了显得具体而虚构数字。
- 用户看不出新版本比原文好在哪里。

## 核心流程

### 首次请求

用户选定 section、field 或 bullet 并输入优化目标。服务端仅使用当前编辑切片和用户指令，返回以下联合结果之一：

1. `ready`
   - 原文信息足够。
   - 返回优化稿和 1～3 条改进说明。
   - 前端直接进入现有 Diff。

2. `needs_input`
   - 缺少会影响真实性或改写价值的关键信息。
   - 返回问题诊断和最多 3 个追问。
   - 不返回伪造的最终稿。

### 补充信息

用户可：

- 回答追问后生成：第二次请求携带原文、原始指令及回答。
- 暂不补充，保守优化：第二次请求明确禁止依赖缺失事实，只重组已有信息。

第二次请求必须返回 `ready`，不得继续追问，避免演变为多轮聊天。

## 追问判定

仅当缺少的信息会显著影响优化质量或真实性时追问，例如：

- 用户要求“量化成果”，原文没有任何结果或规模依据。
- 原文只有职责名词，没有用户采取的具体行动。
- 无法区分用户本人贡献与团队成果。

不得追问：

- 原文已有答案的问题。
- 与本次优化目标无关的问题。
- 要求用户凭空补数字、奖项或业务结果的问题。
- 仅用于让措辞更华丽的问题。

## 输出结构

AI 编辑结果使用可判别联合类型：

```ts
type AIEditResult =
  | {
      status: "ready";
      original: unknown;
      suggested: unknown;
      improvements: string[];
    }
  | {
      status: "needs_input";
      original: unknown;
      diagnosis: string;
      questions: Array<{
        id: string;
        question: string;
        placeholder?: string;
      }>;
    };
```

补充信息请求额外携带：

```ts
type AIEditAnswers = Record<string, string>;
```

问题 ID 由服务端清洗为稳定的 `question-1`、`question-2`、`question-3`，不信任模型原始 ID。

## 提示词策略

提示词将优化定义为“提升信息密度和可验证性”，而不是普通润色：

- 使用清晰的行动、对象、方法和结果组织表达。
- 保留公司名、项目名、技术名、时间和已有数字。
- 不得新增原文或用户回答中不存在的事实、数字与因果关系。
- 禁止只改标点、空格、语序或近义词。
- 避免“负责、参与、协助、显著提升”等缺少具体对象的套话。
- `ready` 结果必须包含改进说明，说明结构、重点或信息密度发生了什么变化。

首次请求允许模型选择 `ready` 或 `needs_input`；补充信息请求强制输出 `ready`。

## 前端状态与交互

`AIModal` 复用现有弹窗与 Diff，增加以下状态：

1. 输入指令。
2. 分析中。
3. 需要补充信息。
4. 生成中。
5. Diff 就绪。
6. 错误。

补充信息页显示：

- 一句问题诊断。
- 最多 3 个文本输入框。
- “根据补充信息生成”主按钮。
- “暂不补充，保守优化”次按钮。

Diff 上方显示“本次改进”列表。采纳、放弃、关闭行为保持不变。

## 服务端校验

服务端不直接透传模型结果：

- `questions` 最多保留 3 条，过滤空问题并重建 ID。
- `improvements` 最多保留 3 条，过滤空内容。
- `ready` 必须包含结构有效的 `suggested`。
- `suggested` 与 `original` 完全相同时视为无效结果并返回可理解的错误。
- 第二阶段若模型仍返回追问，视为非法结果。
- 原有 section / bullet 结构约束继续保留。

## 错误处理

- 分析或生成失败：保留原文，不修改版本仓库。
- 补充信息为空：允许选择保守优化，不强制伪造答案。
- 非法 JSON、超时和连接错误：沿用现有错误文案与重试入口。
- 关闭弹窗：清空本次诊断、问题和回答，不产生任何修改。

## 测试

新增以纯函数和 mock 请求为主的最小测试：

- 信息充分时清洗为 `ready`。
- 信息不足时清洗为 `needs_input`，问题不超过 3 条且 ID 稳定。
- 第二阶段只接受 `ready`。
- 空问题、空改进说明和无变化建议被正确处理。
- 原有 section、field、bullet 改写结构保持兼容。
- 接受建议仍只修改目标板块或目标 entry 版本。

## 验收标准

- 普通润色在信息充分时仍可一次完成。
- 需要量化或补充事实时才出现追问。
- 用户可跳过追问并获得不编造事实的保守优化稿。
- Diff 能明确展示新旧内容和具体改进点。
- AI 失败、取消或拒绝建议都不会修改简历内容。
- JD 定制、版本管理、自动保存与 PDF 导出行为不变。
